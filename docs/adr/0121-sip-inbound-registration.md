# ADR-0121: Входящие по регистрации у SIP-провайдера — агент `calab-sipreg` (B2BUA) перед LiveKit SIP (2026-10-22)

**Статус: предложено** (документ без кода; реализация — отдельной задачей после ответов владельца на вопросы
в конце). Дополняет [ADR-0117](0117-sip-inbound-ivr.md) (входящие на SIP-номер: транк, dispatch-правило,
комната `sipin_<ws>_*`, машина состояний, воркер `calab-ivr`) и [ADR-0046](0046-sip-telephony.md) (аккаунт
провайдера `sip_accounts`, пароль в sealbox, транк исходящих). Опирается на [ADR-0013](0013-livekit-minimal-client.md)
(в API нет pion / `livekit/protocol`) и на решение ADR-0117 §2 «API — голова, рядом с LiveKit — руки».
Задача CBF-65 (#65).

## Контекст

Владелец (22.10): «нужны оба режима входящих — (а) провайдер шлёт вызовы на наш IP, (б) наша регистрация у
провайдера (REGISTER), по ней приходят звонки. Сейчас у провайдера работает регистрация, значит (б) обязательно».

### Что есть (проверено по main, 22.10)

- **Режим (а) реализован** (ADR-0117, шаг 2, `internal/sip/inbound.go`): `PUT /api/workspaces/{id}/sip/inbound
  {enabled, target, allowed_cidrs}` создаёт в LiveKit `SIPInboundTrunk` (`numbers` = Caller ID с «+» и без,
  `allowed_addresses` = A/AAAA хоста провайдера на момент сохранения ∪ `SIP_INBOUND_ALLOWED_ADDRESSES` ∪ диапазоны
  пространства не шире /16) и `SIPDispatchRule` «комната на звонок» (`sipin_<ws>`); один номер — одно
  пространство на сервере (уникальный индекс, 409). Вебхук `participant_joined` линии → `InboundJoined` →
  машина состояний (`machine.go`), воркер `calab-ivr` (`cmd/ivr`) по исходящему WebSocket
  `GET /api/internal/ivr-agent` с `IVR_AGENT_TOKEN`, команды через Redis-канал `ivr:cmd` (`internal/ivr/hub.go`).
  Всё за флагом `SIP_INBOUND=1`; `sip.yaml.tpl` отдаёт `hide_inbound_port: ${SIP_HIDE_INBOUND}`.
- **LiveKit SIP не регистрируется у провайдера.** `livekit/sip` v1.14.0 (пара к `livekit-server v1.13.7`,
  обновлять вместе) умеет только принимать INVITE на свой порт 5060 и слать INVITE по исходящему транку с
  digest-аутентификацией. Проверка настроек «Проверить подключение» — тестовый исходящий звонок (ADR-0046).
- **Почему провайдеру нужна регистрация.** Провайдер с «SIP-аккаунтом» (логин/пароль, как у настольного
  телефона) доставляет входящие только на контакт, который этот аккаунт зарегистрировал (`REGISTER` →
  `Contact: <sip:user@IP:port>`), и обновляет привязку по `expires` (обычно 60–3600 с). Без регистрации у
  такого провайдера входящих нет вообще; IP-транк («переадресация на SIP URI») у него может отсутствовать или
  стоить отдельно.
- **Стенд**: один хост с публичным IPv4 без NAT (`141.105.69.177`, iptables с финальным DROP, docs/03),
  `livekit/sip` и `calab-ivr` в `network_mode: host`; открыто 5060 udp/tcp и 10000–10200/udp только при
  `SIP_ENABLED=1`. Прод-API — в Kubernetes, LiveKit/SIP — на стенде; стыкуются только по HTTPS (вебхуки,
  исходящий WS воркера). Свободные порты на стенде — всё, кроме 80/443/7881/7882/5060/10000–10200/20000–29999
  и чужих 8000–8400/9100/9400.
- **Секреты**: пароль провайдера — `sip_accounts.password_enc`, sealbox `calaba/sip-password/v1`; у каждого
  вида секрета своя цель (`calaba/workspace-ai-key/v1`, `calaba/caldav/v1`, …), секреты не в env и не в логах.

### Что нужно

Компонент, который от имени аккаунта пространства держит регистрацию у провайдера (REGISTER с digest,
обновление, keepalive) и доставляет пришедшие по ней INVITE в LiveKit SIP так, чтобы дальше всё работало
**как в режиме (а)**: тот же транк/правило, та же комната `sipin_*`, та же машина состояний, тот же воркер,
те же модалки. Оба режима — в одной модели аккаунта, выбор — настройкой пространства.

## Решение

### 1. Компонент: Go-агент `calab-sipreg` рядом с `livekit/sip`

Принято: **отдельный маленький Go-бинарник `apps/server/cmd/sipreg`** (тот же Go-модуль, как `cmd/ivr`),
отдельный образ (`apps/server/Dockerfile.sipreg`, distroless), compose-сервис `sipreg` в профиле `ivr`
(поднимается вместе с воркером при `SIP_INBOUND=1`), `network_mode: host`, одна реплика. SIP-стек —
библиотека `github.com/emiago/sipgo` (чистый Go, без cgo и pion; на ней же построен сам `livekit/sip` —
проверить версию при реализации). Бинарник ≈ 15 МБ, RSS ≈ 20 МБ, в простое — только таймеры регистраций.

Агент — «руки», как `calab-ivr`: **не знает БД, прав и пространств**, держит исходящий WebSocket к API
(`GET /api/internal/sipreg-agent`, свой токен `SIPREG_AGENT_TOKEN`; неверный токен — 404, как у воркера),
получает от API список аккаунтов в режиме регистрации и сообщает события. Входящих HTTP-портов у агента нет.
Общая часть с воркером (hello, переподключение с backoff, кадры JSON) выносится в пакет `internal/agentwire`
при реализации, если дублирование окажется заметным; иначе — свой `internal/sipregwire`.

Почему не иначе:
1. **Kamailio / OpenSIPS** (модуль `uac` с таблицей `uacreg`) перед `livekit/sip` — отклонено: второй
   экосистемный компонент с конфигом на своём языке, учётные данные пришлось бы класть в таблицу открытым
   текстом (ломает sealbox) или гонять через RPC-reload; регистрации «из БД» не стыкуются с API в k8s;
   образ и память на порядок больше ради одной функции.
2. **Asterisk / FreeSWITCH как B2BUA с регистрацией** — отклонено: якорят и перекодируют медиа (вторая
   медиа-точка, CPU, задержка), 100+ МБ, конфиг файлами, та же проблема с секретами.
3. **Регистрация внутри `calab-ivr`** — отклонено: воркер несёт pion и медиа, падает и перезапускается по
   своим причинам; регистрация должна жить максимально стабильно и независимо. Паттерн связи с API — тот же.
4. **Регистрация в API-процессе** — отклонено: API в k8s без публичного UDP и без стабильного адреса,
   Contact должен указывать на хост, где слушает LiveKit SIP (стенд); API stateless (ADR-0013, docs/01).
5. **Ждать регистрацию в `livekit/sip`** — её нет в v1.14 и в дорожной карте не обещана; если появится —
   агент убирается, модель (§3) остаётся. Проверять при каждом обновлении пары server/sip.

### 2. Протокол: регистрация, приём INVITE, передача в LiveKit SIP

**Регистрация (UAC).** На каждый аккаунт в режиме `register` агент держит регистрацию у
`reg_registrar` (хост:порт, по умолчанию `host:port` аккаунта) по `transport` аккаунта (udp/tcp; tls — §4):
- `REGISTER sip:<domain>` с `From/To: <sip:<username>@<domain>>`, `Contact: <sip:<contact_user>@<PUBLIC_IP>:<port>;transport=…>`,
  `Expires: <reg_expires>` (запрашиваем 600 с; действует то, что вернул провайдер), стабильный `Call-ID` на
  аккаунт, растущий `CSeq`; `401/407` → digest (MD5 и SHA-256 по RFC 8760, `qop=auth`, `auth_username ||
  username`); повтор с учётными данными один раз на challenge (`stale=true` — ещё раз с новым nonce).
- **`contact_user` — не логин, а непрозрачный токен аккаунта** (20+ случайных символов base32, хранится в
  `sip_accounts.reg_contact_user`): по нему агент однозначно узнаёт аккаунт по Request-URI входящего INVITE
  (провайдер шлёт INVITE на зарегистрированный Contact; DID-номер в таком INVITE может быть в `To`, в
  `P-Called-Party-ID` или отсутствовать вовсе — на него полагаться нельзя), а сканерам нечего угадывать.
- Обновление — на 50 % срока, выданного провайдером (`expires` в Contact ответа или заголовке `Expires`),
  но не раньше чем через 30 с и не позже чем за 30 с до конца, с джиттером ±10 %. Снятие регистрации
  (аккаунт выключен / переведён в режим `direct` / удалён) — `REGISTER` с `Expires: 0`.
- **Отказы**: `401/403` после ответа с учётными данными — `failed/auth`, следующая попытка через 5 мин
  (провайдер блокирует за частые неверные пароли); таймаут/5xx/сетевая ошибка — экспоненциальный backoff
  5 → 10 → 20 → … → 300 с с джиттером, статус `failed/<код или timeout>`; успех сбрасывает backoff. Логи —
  только username, realm, код ответа, Call-ID; **никогда** `Authorization`/`WWW-Authenticate` целиком и пароль.

**Keepalive и живость провайдера.** UDP: `OPTIONS sip:<domain>` каждые 30 с (`reg_keepalive_sec`, 0 =
выключен) — держит привязку в промежуточных NAT/файрволах и ловит «тихую» смерть провайдера: два OPTIONS без
ответа → перерегистрация немедленно. TCP: ping двойным CRLF (RFC 5626 §4.4.1) каждые 30 с, разрыв соединения
→ переподключение и REGISTER. На OPTIONS/NOTIFY провайдера (qualify) отвечаем `200 OK`; на всё прочее от
провайдера вне диалога, кроме INVITE, — `405`.

**Приём INVITE (UAS, публичный порт агента, §4).** Пакет принимается к разбору только если адрес источника
∈ множество адресов аккаунтов (резолв `host`/`reg_registrar` при загрузке и раз в сутки ∪ `allowed_cidrs`
пространства ∪ `SIP_INBOUND_ALLOWED_ADDRESSES`); **всё остальное отбрасывается молча**, без ответа (как
`hide_inbound_port` у LiveKit SIP: сканер не должен узнать, что порт живой). Далее: `contact_user` в
Request-URI известен и принадлежит аккаунту этого адреса → звонок; иначе `404`. Повторный INVITE с тем же
Call-ID — ретрансмиссия (transaction layer sipgo). Лимиты: ≤ 60 INVITE/мин на адрес источника и ≤ 10
одновременных незавершённых INVITE-транзакций на аккаунт; сверх — `503` c `Retry-After`. Это первый фильтр;
вторым остаётся API (лимиты пространства, тариф, `inbound_enabled`) — как в режиме (а).

**Передача в LiveKit SIP — B2BUA только по сигнализации, SDP без изменений.** Принято: агент — UAS для
провайдера (нога A) и UAC для `livekit/sip` на `127.0.0.1:5060` (нога B); два диалога, два Call-ID; тело SDP
копируется между ногами как есть (включая `Content-Type`), медиа идёт **напрямую** провайдер ↔ LiveKit SIP
(RTP 10000–10200, `use_external_ip`), агент пакеты RTP не видит. На ноге B:
- Request-URI и `To` — `sip:<caller_id>@127.0.0.1:5060` (номер пространства, нормализованный: так транк
  LiveKit находится по `numbers` независимо от того, как провайдер оформил вызываемый номер);
- `From`, `P-Asserted-Identity`, `Remote-Party-ID`, `Privacy` — переносятся (номер звонящего →
  `sip.phoneNumber` линии, модалка и журнал — как сейчас);
- `X-Calab-Provider-Call-ID: <Call-ID ноги A>` — для корреляции (в атрибут участника через
  `headers_to_attributes` транка, §9 «Проверить»);
- `401/407` от LiveKit SIP (транк режима `register` защищён digest, §4) → ответ с внутренними учётными
  данными транка; `100/180/183/200` → соответствующие ответы провайдеру с Contact агента; `ACK`, `BYE`,
  `CANCEL`, `INFO` (DTMF через INFO разбирает `livekit/sip`), `UPDATE`, re-INVITE (hold) — транслируются в
  обе стороны; `100rel`/`PRACK` и `timer` снимаются из `Require`/`Supported` на ноге B (LiveKit SIP их не
  обещает), на ноге A агент отвечает `Session-Expires` с `refresher=uac`, и re-INVITE провайдера с тем же SDP
  гасит сам, не беспокоя LiveKit; с новым SDP — транслирует.
- Нет ответа LiveKit SIP за 8 с → `503` провайдеру и событие API; `DeleteRoom` в API кладёт линию — LiveKit
  SIP шлёт `BYE` агенту (Contact ноги B — агент), агент — `BYE` провайдеру.

Почему B2BUA, а не SIP-прокси с `Record-Route` (меньше кода: прокси sipgo ~200 строк): (1) провайдер
обязан слать in-dialog запросы на зарегистрированный контакт и часто проверяет источник — у B2BUA провайдер
видит **только** агент (адрес и порт регистрации), у прокси — Contact LiveKit SIP `IP:5060`, и BYE/re-INVITE
LiveKit SIP ушли бы провайдеру напрямую, если `livekit/sip` не соблюдает маршрут `Record-Route` (не проверено
и нам не подконтрольно); (2) прокси не может ответить на digest-challenge LiveKit SIP — транк пришлось бы
доверять по адресу `127.0.0.1`, что открывает любой процесс хоста (включая чужую GPU-задачу); (3) B2BUA
нормализует вызываемый номер и чужие заголовки, изолирует причуды провайдера от LiveKit. Цена — ~600–800
строк Go на двух диалоговых кэшах sipgo и тесты (§7); медиа при этом не трогаем, так что по CPU и задержке
B2BUA равен прокси.

### 3. Модель: два режима в одном аккаунте

Миграция — следующая свободная на момент реализации (на 22.10 вышла `00111`). `sip_accounts` +:
- `inbound_mode text NOT NULL DEFAULT 'direct' CHECK (direct|register)` — режим входящих; исходящие от
  режима не зависят (транк `SIPOutboundTrunk` — как сейчас, см. вопрос 4).
- `reg_registrar text` (хост[:порт] регистратора/outbound proxy; пусто = `host:port`), `reg_domain text`
  (SIP-домен AOR; пусто = `host`), `reg_expires int NOT NULL DEFAULT 600 CHECK (60..3600)`,
  `reg_keepalive_sec int NOT NULL DEFAULT 30 CHECK (0 | 15..120)`, `reg_contact_user text` (токен Contact,
  генерирует API при первом включении режима; `UNIQUE WHERE <> ''`).
- `reg_auth_username text`, `reg_password_enc bytea` — **необязательные** учётные данные регистрации, если у
  провайдера они отличаются от учётных данных транка; пусто = `auth_username || username` и `password_enc`
  аккаунта. Шифрование — **своя цель sealbox `calaba/sip-register/v1`** (как у ключа ИИ — отдельная цель на
  вид секрета; утечка ключа одной цели не раскрывает другие).
- `reg_trunk_password_enc bytea` — внутренний пароль digest транка LiveKit режима `register` (32 случайных
  байта, генерирует API, та же цель `calaba/sip-register/v1`); `auth_username` транка — `reg_contact_user`.
- Состояние (пишет API по событиям агента, не чаще раза в 10 с на аккаунт, кроме смен статуса):
  `reg_status text NOT NULL DEFAULT 'off' CHECK (off|unavailable|registering|registered|failed)`, `reg_error
  text` (код/причина без секретов), `reg_registered_at timestamptz`, `reg_expires_at timestamptz`,
  `reg_contact text` (что реально зарегистрировано, с публичным адресом).
- Уникальность регистрации: `UNIQUE (lower(coalesce(nullif(reg_domain,''), host)), username) WHERE inbound_mode
  = 'register' AND enabled` — одни учётные данные нельзя регистрировать из двух пространств с одного адреса
  (провайдер оставит одну привязку, звонки «пропадут» непредсказуемо); `409 SIP_REGISTRATION_TAKEN`.
- `sip_calls` +: `provider_call_id text` (Call-ID ноги A; у режима `direct` и исходящих — пусто).

**Транк и правило LiveKit в режиме `register`** — те же `makeInboundLK`/`syncInbound` (ADR-0117 шаг 2) с
другими параметрами: `allowed_addresses = ["127.0.0.1"]` (INVITE приходят от агента по loopback),
`auth_username = reg_contact_user`, `auth_password = <reg_trunk_password>`, `headers_to_attributes
{"X-Calab-Provider-Call-ID": "calab.providerCallId"}`; `numbers`, dispatch-правило, `max_call_duration`,
`sipin_<ws>` — без изменений. Смена режима = удалить → создать транк и правило, как при любом сохранении.

**Что получает агент** (снимок при `hello` и дельты `account_set`/`account_del`, только по WS поверх TLS, в
памяти агента, на диск — никогда): `{ws_id, contact_user, registrar, domain, transport, username,
auth_username, password, expires, keepalive_sec, allowed_sources[], number, trunk_auth {user, password}}`.
Пароли расшифровывает API в момент отправки; при обрыве WS агент продолжает работать с последним снимком
(регистрации и звонки не прерываются) и после переподключения получает снимок заново (удалённые аккаунты —
снятие регистрации).

**События агента → API**: `registration {ws_id, status, error, expires_at, contact}` (при смене и раз в
10 мин как heartbeat), `invite {ws_id, provider_call_id, leg_b_call_id, from, to, source}`, `invite_result
{ws_id, provider_call_id, code}` (как завершилась транзакция INVITE: 200, 4xx/5xx, отменён), `bye {ws_id,
provider_call_id, by: provider|livekit}`. API: обновляет `reg_*`, пишет `provider_call_id` в `sip_calls`
(сопоставление с линией — по атрибуту `calab.providerCallId` в `InboundJoined`, запасной путь — по
`leg_b_call_id` = `sip.callID`), считает метрики. Машина состояний ADR-0117 событий агента **не ждёт**:
звонок начинается с `participant_joined` линии, как в режиме (а).

### 4. Безопасность

- **Публичный порт агента** — `SIP_REGISTRAR_PORT` (по умолчанию **5080** udp+tcp; 5060 занят LiveKit SIP,
  порт входит в Contact, провайдеру он безразличен). Файрвол стенда: два правила `calaba-sipreg` перед DROP
  только при `SIP_INBOUND=1`. На порту **нет ответов неизвестным**: источник вне адресов провайдеров —
  тишина (ни 403, ни 404: SIP-сканеры ищут живые порты и аккаунты по ответам, а UDP-ответ чужому адресу —
  усилитель). Известный провайдер и чужой Request-URI — `404`, но не более 10 ответов/с на адрес.
- **Подмена регистрации.** (1) Регистрацию на провайдере защищает его digest — наш пароль; API требует
  пароль длиной ≥ 8 (как сейчас), UI советует сгенерированный провайдером. (2) Ложные ответы на наш REGISTER
  (`200 OK` от чужого) — транзакция сверяется по `branch` Via, Call-ID, CSeq и To-tag; подделка требует
  on-path позиции; закрывается TLS (ниже). (3) Ложные INVITE «от провайдера» — только с адресов провайдера и
  на непредсказуемый `contact_user`; при желании провайдера аутентифицировать INVITE (редко) — поддержка
  401-challenge на ноге A вне v1. (4) Агент **не регистратор для других**: чужой `REGISTER` — тишина; агент
  форвардит INVITE только на `127.0.0.1:5060` и только для известных аккаунтов — открытым релеем быть не
  может.
- **Транк LiveKit режима `register`** защищён адресом `127.0.0.1` **и** digest (`auth_username/auth_password`
  транка): процесс на том же хосте без пароля транка (а он есть только у API и в памяти агента) звонок в
  пространство не вставит. Транк режима `direct` остаётся как в шаге 2.
- **TLS к провайдеру** (SIP over TLS, 5061) — в v1 нет: нужен сертификат на домен стенда для SIP-порта
  агента (Caddy выпускает для `rtc.<domain>` — можно переиспользовать файл сертификата через общий volume,
  но это новое сцепление) и провайдер, который TLS даёт. Заложено в `transport` (`tls` уже в CHECK), включать
  отдельной задачей (вопрос 7). SRTP не делаем — медиа у LiveKit SIP, его настройка.
- **Секреты**: пароли провайдера и транка — только в БД (sealbox) и в памяти агента; по WS — поверх TLS к
  `https://app.calab.io`; в логах агента и API — нет (структурные поля `user`, `realm`, `code`, `call_id`,
  `source`); номер звонящего в логах агента маскируется до последних 4 цифр (в журнале `sip_calls` — полный,
  как сейчас). `SIPREG_AGENT_TOKEN` — отдельный от `IVR_AGENT_TOKEN` (разные привилегии: воркер получает
  файлы и токены комнат, агент — пароли провайдеров). Снимок `GET …/sip` пароли и `reg_contact_user` не
  отдаёт (`has_password`, `has_reg_password`; Contact показывается с замаскированным user-part).
- **Rate limiting в API**: как у режима (а) — `rl:sip-in:` 60/ч и ≤ 5 одновременных на пространство
  (`InboundJoined`); смена режима/учётных данных — не чаще 10 раз в час на пространство (каждая — REGISTER у
  провайдера).
- **Второе независимое ревью безопасности обязательно** (как в ADR-0117): новый публичный SIP-порт, пароли
  провайдеров по WS, digest-реализация, B2BUA-парсинг чужого SIP.

### 5. NAT, адреса, Contact

- Публичный адрес Contact — `SIP_REGISTRAR_PUBLIC_IP` (на стенде IP статический, без NAT); пусто → STUN
  (`SIP_REGISTRAR_STUN`, по умолчанию тот же сервер, что у `livekit.yaml.tpl`), как `use_external_ip` у
  LiveKit SIP. Адрес узнаётся на старте и раз в 10 мин; смена — перерегистрация всех аккаунтов.
- Via с `;rport` (RFC 3581): если в ответе `received`/`rport` расходятся с Contact (агент за NAT — не стенд,
  а будущий чужой хост) — агент перерегистрируется с увиденным адресом («learned contact», как `nat=yes` в
  Asterisk) и пишет это в `reg_contact`. Keepalive (§2) держит NAT-привязку: 30 с короче типичного UDP-таймаута.
- IPv6: на стенде нет; Contact — только IPv4 в v1.

### 6. Отказоустойчивость и наблюдаемость

- Агент — одна реплика (`replicas: 1`, две зарегистрировали бы один Contact дважды — провайдеры ведут себя
  по-разному; горизонтальное масштабирование не в v1), `restart: unless-stopped`; при рестарте — REGISTER всех
  аккаунтов сразу (прежняя привязка у провайдера с тем же Contact просто обновляется), живые звонки при
  рестарте агента **теряют сигнализацию** (медиа идёт, но BYE не дойдёт) — LiveKit кладёт линию по
  `max_call_duration`/RTP-таймауту; принимаем, рестарты агента редки (нет медиа, нет зависимостей кроме сети).
- Нет соединения с агентом → API ставит всем аккаунтам режима `register` `reg_status = unavailable` (баннер в
  настройках «Регистратор недоступен»), новые включения режима — `409 SIP_DISABLED` «SIP-регистратор не
  настроен» (как у воркера); API без агента ≥ 2 мин — `WARN` в логах.
- Метрики API (`/metrics`): `calab_sip_registrations{status}`, `calab_sip_registration_failures_total{reason}`,
  `calab_sip_register_invites_total{result}`; агент — метрик не отдаёт (нет портов), пишет JSON-логи.
  Переходы `registered → failed` — `WARN` с `ws_id`, `reg_error`. Стенд-агент в чек-листе релиза:
  `docker compose logs sipreg | grep -c '"status":"registered"'` ≥ числа аккаунтов.
- Владельцу/админу: статус регистрации и `reg_error` в карточке «Входящие» (вопрос 5 — нужно ли уведомление в
  приложение при длительном сбое).

### 7. Стенд, прод и тестирование без провайдера

- **Стенд**: агент живёт **на стенде** рядом с `livekit/sip` (публичный IP, loopback к 5060); `.env`:
  `SIP_INBOUND=1` (уже есть) + `SIPREG_AGENT_TOKEN`, опционально `SIP_REGISTRAR_PORT`, `SIP_REGISTRAR_PUBLIC_IP`;
  `deploy.sh` добавляет сервис `sipreg` в тот же профиль `ivr`; файрвол — два правила на 5080. API прода
  (k8s): `SIPREG_AGENT_TOKEN`; ingress пропускает `/api/*` — путь `/api/internal/sipreg-agent` подходит.
  **От владельца**: провайдер и учётные данные SIP-аккаунта для стенда (хост/домен регистрации, логин,
  пароль, номер), допускает ли провайдер регистрацию с нашего IP (белые списки) и с нестандартного порта
  Contact (5080), поддерживает ли TCP/TLS, какой `expires` выдаёт.
- **Образ** `calab-sipreg` — в `images.yml` вместе с `calab-ivr` (его там пока нет — docs/12 от 22.10 (в)).
- **Тесты без провайдера** — три уровня:
  1. `go test` агента: **фейковый провайдер in-process на sipgo** (регистратор с digest-challenge, выдачей
     `expires`, `stale`, отказами 401/403/5xx, OPTIONS; UAC, шлющий INVITE на зарегистрированный Contact) и
     **фейковый LiveKit SIP** (UAS на loopback с digest-challenge, 180/200, BYE) — проверяют регистрацию,
     обновление, backoff, B2BUA-поток, CANCEL, BYE с обеих сторон, re-INVITE, трансляцию INFO;
  2. интеграционный тест API (`-tags integration`) с фейковым агентом (как фейк воркера в шаге 2): снимок
     аккаунтов при `hello`, дельты, события `registration`/`invite`, `reg_status`, `provider_call_id`;
  3. ручная сквозная проверка в dev: контейнер **Asterisk** (`compose.dev.yml`, профиль `sip-dev`:
     `pjsip.conf` с эндпоинтом-аккаунтом, `max_contacts=1`, `qualify`, диалплан «позвонить на
     зарегистрированный контакт и проиграть файл») как провайдер + настоящие `livekit/sip` и `calab-ivr` —
     слышен ли звук меню, доходит ли DTMF, кладётся ли трубка с обеих сторон. SIPp-сценарии (`tools/sip/`)
     — для нагрузки по желанию, не обязательны.

### 8. Клиент и контракт (кратко)

- Карточка «Входящие» (ADR-0117 §7) получает переключатель **«Как приходят звонки»**: «Провайдер шлёт на наш
  адрес» (режим `direct`: адреса провайдера, как сейчас) / «По регистрации у провайдера» (режим `register`:
  поля регистратор/домен (свёрнуты, по умолчанию = хост), отдельные учётные данные регистрации (свёрнуты,
  «если отличаются»), интервал регистрации; строка состояния «Зарегистрировано до 14:32 · контакт
  sip:c…@141.105.69.177:5080» / «Ошибка: 401 — неверный пароль» / «Регистратор недоступен»). Состояние
  перечитывается `GET …/sip` каждые 15 с, пока вкладка видна (без нового события gateway).
- `sip.proto`: `SipInboundMode {UNSPECIFIED, DIRECT, REGISTER}` — `UNSPECIFIED` в `PutSipInboundRequest`
  значит «не менять» (старые клиенты шага 2 не сбросят режим); `SipRegistration {registrar, domain, expires_sec,
  keepalive_sec, auth_username, has_password, status (OFF|UNAVAILABLE|REGISTERING|REGISTERED|FAILED), error,
  registered_at, expires_at, contact_masked}` в `SipSettings.registration`; `PutSipInboundRequest` +: `mode`,
  `registration {registrar, domain, expires_sec, keepalive_sec, auth_username, password?}` (пароль не слать =
  не менять, `""` = убрать → учётные данные транка). Ошибки: `409 SIP_REGISTRATION_TAKEN` (новый код
  `common.proto`, следующий свободный — 71 на 22.10), `409 SIP_DISABLED` (агент не настроен), `422 VALIDATION`
  с `field` (`registrar`, `domain`, `expiresSec`, `keepaliveSec`, `regAuthUsername`, `regPassword`). Новых
  `DispatchEvent` нет. `SipCall.provider_call_id` — в журнал (`VIEW_JOURNALS`).
- Права — те же `MANAGE_INTEGRATIONS` (ADR-0117 §5), боты — так же.

### 9. Как сочетается с реализованным шагом 2

Ничего в потоке звонка после LiveKit SIP не меняется: транк и dispatch-правило создаются тем же
`syncInbound`, комната `sipin_<ws>_*`, `InboundJoined`, машина состояний, воркер `calab-ivr`, `accept`/
`decline`/`hangup`, события `SIP_INBOUND_RING`/`SIP_CALL_UPDATE`, журнал — как есть. Меняются только:
(1) кто приносит INVITE в LiveKit SIP — провайдер напрямую (`direct`) или агент по loopback (`register`);
(2) параметры транка (`allowed_addresses`, `auth_*`, `headers_to_attributes`) — ветка в `makeInboundLK` по
`inbound_mode`; (3) `InboundJoined` дописывает `provider_call_id` по атрибуту; (4) `rtc.SIPInboundTrunk`
растёт на `AuthUsername`, `AuthPassword`, `HeadersToAttributes`; (5) хаб агента — второй экземпляр паттерна
`internal/ivr/hub.go` (канал `sipreg:cmd`, снимок при `hello`). «Один номер — одно пространство» (фикс ревью
шага 2) действует для обоих режимов. Тарификация абонента с `200 OK` LiveKit — та же особенность.

- Новый деплой-юнит `calab-sipreg` (бинарник, образ, compose-сервис, env, два правила файрвола, `images.yml`),
  новая зависимость модуля `emiago/sipgo` только в `cmd/sipreg` (API-бинарник не растёт, ADR-0013 соблюдён).
- Миграция (`sip_accounts` + 14 колонок, `sip_calls.provider_call_id`), новая цель sealbox
  `calaba/sip-register/v1`, хаб `internal/sipreg`, правки `internal/sip` (режим в `makeInboundLK`, валидация,
  статус), `rtc.SIPInboundTrunk`, proto, UI карточки «Входящие», docs/03 (порт 5080), docs/06 (шаги включения,
  чек-лист стенд-агента), TESTING.md (сценарий ≤ 15 строк).
- Второе независимое ревью безопасности; реальный провайдер нужен для приёмки (без него — Asterisk в dev).

## Проверить в реализации

1. `livekit/sip` v1.14.0: inbound-транк с `auth_username/auth_password` действительно шлёт 401/407 на INVITE
   и принимает digest; `headers_to_attributes` есть в этой версии протокола и работает в OSS; как сервис
   определяет адрес источника для `allowed_addresses` (транспортный адрес `127.0.0.1`, а не Via).
2. `livekit/sip` отвечает на INVITE с SDP, где `c=` — публичный адрес провайдера, с ноги B по loopback: RTP
   должен уйти на провайдера с внешнего адреса (`use_external_ip`), а не на 127.0.0.1 (симметричный RTP).
3. Что провайдер владельца кладёт в Request-URI и `To` входящего по регистрации, присылает ли `P-Asserted-Identity`,
   принимает ли исходящие INVITE транка LiveKit (с 5060) при регистрации с 5080 (вопрос 4), нужен ли ему
   `Expires` ≤ 600.
4. Версия `sipgo` у `livekit/sip` v1.14 и у нас — не обязаны совпадать, но известные несовместимости парсера
   (multipart SDP, `Record-Route` с параметрами) лучше проверить одной версией.
5. CPU агента в простое с 1–10 регистрациями — должен быть ≈ 0 (таймеры, редкие пакеты); OPTIONS раз в 30 с
   на аккаунт.

## Открытые вопросы владельцу

1. **Провайдер и доступ для стенда.** Какой провайдер и какой номер? (а) дать стенду учётные данные
   SIP-аккаунта (хост/домен, логин, пароль) — реализация проверяется на живом провайдере; (б) только локальный
   Asterisk, живая проверка — после передачи вам. Рекомендую (а): особенности INVITE по регистрации у каждого
   провайдера свои (§ «Проверить» 3).
2. **Режимы в пространстве.** (а) один режим на пространство — либо «на наш адрес», либо «по регистрации»
   (рекомендую, v1); (б) оба одновременно (два транка на один номер) — сценария нет, сложнее.
3. **Публичный порт регистрации.** (а) 5080 udp/tcp на стенде, ещё два правила файрвола (рекомендую);
   (б) поменять местами: агент на 5060, LiveKit SIP на другом порту — пришлось бы менять адрес у провайдеров
   режима (а).
4. **Исходящие при регистрации.** (а) как сейчас — транк LiveKit шлёт INVITE с digest с порта 5060
   (рекомендую; большинство провайдеров принимают аутентифицированный INVITE независимо от регистрации);
   (б) если провайдер требует исходящие строго с зарегистрированного контакта — исходящие тоже через агент
   (ещё ~неделя, отдельная задача).
5. **Сбой регистрации — как узнаёте.** (а) статус и ошибка в настройках телефонии + логи/метрики (v1);
   (б) плюс системное сообщение админам с `MANAGE_INTEGRATIONS` после 10 мин сбоя (+2 дня); (в) только проверка
   стенд-агентом перед релизом. Рекомендую (а) сейчас, (б) следом.
6. **Учётные данные регистрации.** (а) те же, что у транка исходящих (логин/пароль аккаунта), отдельные поля
   свёрнуты «если отличаются» (рекомендую); (б) всегда отдельные видимые поля.
7. **TLS к провайдеру.** (а) UDP/TCP в v1, TLS — отдельной задачей, когда понадобится (рекомендую);
   (б) TLS сразу — сертификат для SIP-порта стенда и провайдер с TLS, +3 дня.
8. **Где живёт агент.** (а) на стенде рядом с LiveKit SIP (рекомендую: публичный IP, loopback к 5060);
   (б) в k8s — потребует публичный UDP-ingress/hostNetwork, не рекомендую.
9. **Вызываемый номер.** По регистрации звонок может прийти без номера в INVITE — считаем каждый такой
   звонок звонком на номер пространства (Caller ID). Если у аккаунта несколько номеров на одной регистрации —
   в v1 все идут в одну точку входа; маршрут по номеру — позже (ADR-0117 §9). Устраивает?

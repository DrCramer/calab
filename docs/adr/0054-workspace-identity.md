# ADR-0054: Корпоративная идентификация в границах пространства (2026-10-01)

**Статус: принято, реализовано в 2.0.0 (2026-10-02).**
Автор решения — ведущий агент. Это общий контракт, а не выбор каждого исполнителя.
Уточняет ADR-0023 (локальная идентификация), ADR-0024 (тарифы), ADR-0048 (права);
не меняет назначение веб-ярлыков ADR-0050. Номер 0053 занят решением о высоте веб-приложений.

## Контекст

Владелец запросил корпоративный OpenID Connect SSO и Active Directory для Business и
Enterprise, а также создание OAuth-клиентов внутри пространства для «Войти через Calaba».
У Calaba один пользователь может состоять в нескольких независимых пространствах.
Администратор корпоративного IdP управляет идентичностями своей организации: доверие
его ответу не должно предоставлять доступ к другим организациям, личным данным или
глобальному суперадминистрированию пользователя с совпавшим email.

Нужны два протокольных направления с одной моделью доверия:

```text
Корпоративный IdP ── OIDC ──> Calaba: доступ к пространству A
                                     │
                                     └── OAuth 2.0 + OIDC ──> приложение пространства A
Active Directory ── LDAPS sync ──> состояние членства в A
```

OIDC доказывает вход; синхронизация каталога определяет, кому организация ещё разрешает
доступ. OAuth 2.0 делегирует доступ, OIDC поверх него предоставляет внешнему приложению
проверяемое подтверждение личности. Эти сущности нельзя объединить с bot token или
сохранённой сессией встроенного веб-приложения.

## Решение

1. **Единица доверия — workspace.** Настройка IdP, entitlement, policy, каталог,
   OAuth-клиент, согласие и отзыв всегда имеют workspace_id. Корпоративный вход выдаёт
   `workspace_sso`-сессию, ограниченную этим workspace. Независимый локальный вход
   выдаёт `local_account`-сессию; доступ такой сессии в пространство с обязательным SSO
   требует отдельного свежего SSO-подтверждения. Refresh не меняет область сессии.
2. **Поддерживаемые IdP:** generic OIDC, Entra ID с точным tenant-specific issuer,
   AD FS 2019+ с проверенным PKCE S256. Одна активная OIDC connection на workspace.
   Вход через системный браузер, Authorization Code + PKCE S256, state и nonce.
   Обмен upstream code и валидация ID token — на сервере. Не используем implicit,
   password grant, пароль AD в Calaba или произвольный IdP из callback.
3. **Без автоматического объединения аккаунтов по email.** Внешняя идентичность —
   `(connection_id, issuer, subject)`; привязка к существующему аккаунту требует его
   свежей независимой локальной аутентификации и доказательства внешнего входа.
   Claims IdP не подтверждают глобальный email и не назначают superadmin/owner/admin.
   В первой версии нет JIT создания глобального аккаунта: приглашённый или подготовленный
   участник сначала завершает локальный onboarding и явную привязку; последующие
   самостоятельные входы через SSO доступны без локального пароля, в пределах workspace.
4. **Режимы пространства:** `off`, `optional`, `enforced`. Политика проверяется сервером
   на REST, выдаче/доставке/replay WS-событий, ссылках на ресурсы и RTC. При `enforced`
   пароль, reset, приглашение или старая сессия не заменяют SSO. Гостевой доступ при
   enforced закрыт; уже подключённые гости удаляются. Боты сохраняют отдельную машинную
   модель прав и не получают user SSO/OAuth-сессии.
5. **Business / Enterprise.** В существующем протоколе `PLAN_ENTERPRISE` и SQL
   `enterprise` означают облачный Business. On-prem Enterprise задаётся оператором
   отдельно. Доступ определяется положительным entitlement текущего workspace и
   действующим тарифом/edition, не отрицательным флагом с разрешающим нулём.
   Free, Team, истёкший план и custom без Business/Enterprise основания доступа не дают.
   *Дополнено [ADR-0113](0113-plan-identity-flag-and-overrides.md) (2026-10-20): основание — ещё и
   положительный флаг `corporate_identity` индивидуального тарифа или переопределения Team / Business.*
   Для собственного OAuth-провайдера применяем те же тарифы как явное продуктовое
   допущение этого проекта; владелец отдельно подтвердил тарифы только для SSO/AD.
6. **AD — отдельный lifecycle-канал.** LDAPS sync входит в рабочий план 2.0 как
   архитектурный выбор, а не как утверждение о ранее подтверждённом владельцем объёме.
   Read-only bind, строгая проверка сертификата, immutable objectGUID, явная привязка
   directory object к участнику. Пароли AD не импортируются. Sync раз в 5 минут;
   если последняя полная успешная проверка старше 1 часа, directory-managed доступ
   закрывается. Ошибка сети не означает удаление всех пользователей. Группы в v1
   фильтруют допуск; автоматическое назначение ролей и создание глобальных пользователей
   не входит. Частные сети доступны только по операторскому allowlist; cloud connector
   не включён в этот релиз. Реальная AD/AD FS совместимость требует отдельного стенда.
7. **Calaba — OIDC Provider с issuer на workspace:**
   `${IDENTITY_PUBLIC_ORIGIN}/oidc/workspaces/{workspace_uuid}`. Subject — случайный
   постоянный opaque идентификатор пары `(workspace,user)`, одинаковый для клиентов
   одного workspace, разный между workspace. Это public subject внутри своего issuer,
   не обещание pairwise некоррелируемости. Не раскрываем UUID аккаунта, другие
   пространства, роли или superadmin. Клиент принадлежит ровно одному workspace.
8. **Профиль provider v1:** Authorization Code + S256; scopes `openid profile email`;
   confidential web и public native/SPA clients; явное согласие, UserInfo, rotating
   refresh и revocation. API scopes, client_credentials, dynamic client registration,
   offline_access, SAML, SCIM и глобальный single logout вне первой версии.
   Provider access/refresh — opaque, хранятся хэшами; ID token — RS256 с отдельными
   ключами. Ни один из них не заменяет first-party session/bot/LiveKit token.
9. **Отзыв и восстановление.** Ban, удаление участника, отключение directory object,
   смена policy/connection и истечение entitlement отзывают доступ адресно к workspace.
   Другие workspace и независимые локальные сессии сохраняются. Enforced не становится
   optional при поломке IdP или понижении тарифа. Владелец заранее настраивает recovery:
   это отдельная краткая сессия только для ремонта политики, без чтения чатов и выпуска
   OAuth-токенов. Снятие enforcement — явное действие владельца с аудитом.

Точные API, сроки, сущности, ограничения и критерии приёмки:
[контракт реализации 2.0](../plans/release-2.0-identity.md). Он нормативен вместе с этим
ADR. Исследовательские `next-release-*.md` не являются альтернативными контрактами.
Исполнитель может выбирать локальные приёмы реализации; менять перечисленное решение,
таблицы wire API, сроки или границы доверия самостоятельно нельзя. Расхождение сначала
передаётся ведущему, затем меняется версия контракта и согласуются зависимые задачи.

## Последствия

- Понадобятся явный session authority, workspace assurance, единая policy-функция,
  таблицы identities/каталога/OAuth и сквозная проверка всех каналов. Одной кнопки входа
  и callback недостаточно; обход через любой старый маршрут блокирует релиз.
- Участник с workspace SSO не получает автоматически DM, личные заметки, список других
  организаций и управление глобальными credentials. Для них нужен независимый локальный
  вход; это намеренная граница защиты от администратора чужого IdP.
- Серверные секреты шифруются отдельным keyring с AAD; OAuth client secret только
  хэшируется. Signing keys отдельно от JWT_SECRET; необходимы ротация и backup/restore.
- Уже выданный ID token и сессия на стороннем сайте не могут быть мгновенно отозваны
  Calaba. UserInfo/refresh отказывают после отзыва; RP отвечает за свою session policy.
- Сбой IdP/LDAP или истечение тарифа может временно закрыть корпоративный доступ.
  Это отображается в UI; recovery не открывает данные в обход enforced.
- Выкатываем выключенным, затем test/optional pilot и только после проверки recovery —
  enforced. Откат на бинарник, игнорирующий policy/authority, запрещён.
- До merge нужны целевые тесты и два независимых security/protocol review на итоговом
  commit. Документ не подтверждает их выполнение. Кодеры — Codex SOL, не Claude.

## Основание протокольных решений

OIDC и проверка ID Token — [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html).
Защита code flow и refresh — [OAuth Security BCP, RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html).
PKCE в AD FS с Server 2019 — [Microsoft AD FS flows](https://learn.microsoft.com/en-us/windows-server/identity/ad-fs/overview/ad-fs-openid-connect-oauth-flows-scenarios).
Границы workspace, сроки, отсутствие JIT и набор функций выше — решения Calaba,
а не требования перечисленных стандартов.

# ADR-0103: Вложения задач открываются в просмотрщике; PDF — встроенный просмотрщик Chromium (2026-10-15)

**Статус: принято.**

## Контекст
Владелец, 15.10: файл, прикреплённый к задаче, не скачивается — клик ничего не делает (macOS-приложение).
Причина: чип вложения был `<a href="/api/files/{id}" target="_blank">`. Собранный renderer — страница
`file://`, ссылка разрешается в `file:///api/files/{id}`; `setWindowOpenHandler` отдаёт в браузер
только http(s), остальное — `deny`, то есть тишина. В вебе та же ссылка открывала вкладку без
`Authorization` (файлы API отдаёт только по bearer) — 401. Чат, Диск и почта уже качали
через `platform.files.download`. Просьба заодно: PDF — смотреть в приложении, со «Скачать».

## Решение
1. **Клик по вложению** (`services/files.ts` `openAttachment`, чип `AttachmentChip`): картинка с
   серверной миниатюрой → существующий Lightbox (←/→ по картинкам задачи); PDF до 50 МБ → просмотрщик;
   остальное — `platform.files.download` (десктоп: менеджер загрузок main, `~/Downloads`, карантин;
   веб: fetch с токеном + `<a download>`). Ссылок на `/api/*` в UI нет.
2. **PDF — встроенный просмотрщик Chromium**, не pdf.js. Renderer качает файл с токеном
   (`platform.apiFetch`), заворачивает в `Blob` с типом `application/pdf` (тип ставим сами — не
   сниффится, как HTML не отрисуется) и показывает `blob:`-URL в `<iframe>` внутри оболочки Lightbox
   (`ViewerBar`: имя, размер, «Скачать», «Закрыть»). Прямой фрейм на `/api/files/{id}` не годится:
   сервер отдаёт `Content-Disposition: attachment` и `CSP: sandbox`. Закрытие — abort запроса,
   `revokeObjectURL`, фрейм размонтирован: ничего не работает в фоне.
3. **Что пришлось открыть** (проверено на Electron 44, macOS, отдельным стендом):
   - `plugins: true` **не нужен** — просмотрщик работает с `plugins: false`;
   - CSP renderer-а (`index.html`) и веба (`sites.caddy`, едет в web-образе прода): `frame-src` + `blob:`;
   - навигационные guard-ы (`guardWebContents` и почтовый `mail/frameGuard.ts`, оба на
     `will-frame-navigate`) пропускают подфреймы
     `blob:` нашей страницы (`blob:file:///…`, в dev — `blob:<dev origin>/…`) и страницу расширения
     просмотрщика `chrome-extension://mhjfbmdgcfjbbpaeojofohoefgiehjai/` (`main/pdfFrame.ts`).
     Без любого из двух — пустой просмотрщик. Почтовый guard не пропускает их, если навигацию
     начало само тело письма (`about:srcdoc`).
   - Своя кнопка «Скачать»/печать просмотрщика идёт мимо нашего `downloadFile` (диалог сохранения
     Chromium): обработчик `will-download` ставится на старте и метит карантином/MotW и такие файлы.
4. **Телефон** (WebView Android без PDF) — PDF скачивается, как раньше.

## Почему так
- pdf.js — ~1.3 МБ (worker) лишнего в бандле и свой рендер на canvas, CPU на слабых машинах;
  встроенный PDFium уже в Electron, вынесен в отдельный процесс, с поиском/зумом/печатью.
- Безопасность: `blob:` нашего origin создаёт только наш скрипт; содержимое — PDF, его JS
  (ограниченный PDFium) не видит DOM страницы; preload в подфреймах нет (`sandbox`, contextIsolation).
  Расширение — компонент Chromium с фиксированным id, не устанавливаемое.

## Последствия
- Новые фреймы в renderer — только через этот путь; guard по-прежнему режет всё остальное.
- Если Chromium поменяет id расширения — пустой просмотрщик (виден в e2e `boards-task-pdf`); фикс — `pdfFrame.ts`.
- Чат/Диск продолжают качать PDF по клику; перевести их на `openAttachment` — отдельная задача (docs/09).

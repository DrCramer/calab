# ADR-0112: Своя временная комната встречи (2026-10-19)

**Статус: принято.** Дополняет [ADR-0038](0038-calendar.md) (встречи) и [ADR-0044](0044-temp-rooms.md)
(временные комнаты). Задача CBF-18.

## Контекст
Владелец, 19.10: в диалоге встречи — галочка «Создать временную комнату»; комната создаётся сама за час до
начала, живёт до конца встречи с запасом, называется как встреча, участники видят её во встрече. Раньше
временную комнату со встречей можно было сделать только «сейчас» (`with_event`, ADR-0044), а встречу на
завтра — только в постоянную комнату.

## Решение
1. **Модель.** `events.temp_room boolean` (миграция `00106`, CHECK — только без `rrule`). `temp_room` и
   `room_id IS NULL` — запрос ждёт; `temp_room` и `room_id` задан — это своя комната встречи. Контракт:
   `CalendarEvent.temp_room`, `CreateCalendarEventRequest.temp_room`, `UpdateCalendarEventRequest.temp_room`
   (optional).
2. **Кто просит.** Только сам организатор (комната создаётся от его имени), человек — не бот (`403
   BOT_NOT_ALLOWED`), с `CREATE_TEMP_ROOMS` (`403`); вместе с `room_id` — `422`; **серии — нельзя (`422`, v1)**:
   комната на каждое вхождение — это отдельный механизм и лимиты, отложено. Выбранная вручную комната
   (или её снятие) снимает запрос; `temp_room=false` — тоже (уже созданная комната остаётся обычной комнатой
   встречи).
3. **Когда.** Метёлка календаря (раз в 30 с, на каждом инстансе) забирает встречу `FOR UPDATE SKIP LOCKED`
   в транзакции, которая создаёт комнату, когда до начала ≤ 1 ч и встреча не кончилась. Встреча, которая
   при сохранении (создании или переносе) уже ближе часа, получает комнату сразу, в той же транзакции —
   ответ несёт `room_id`, лимит/права отказывают встрече (`409 TEMP_ROOM_LIMIT`, `403`). Не вышло в метёлке
   (права, лимиты) — повтор на следующем проходе до конца встречи.
4. **Какая.** Тот же код, что `POST …/rooms/temp` (`rooms.insertTemp`): создатель — организатор, название —
   название встречи (≤ 100), публичная, конец = **конец встречи + 1 ч** (как гостевые ссылки встречи;
   в пределах 15 мин … 7 сут от «сейчас»), ссылка комнаты по умолчаниям ADR-0044: пускает гостей, если у
   организатора `INVITE_GUESTS` и подтверждённая почта, иначе «только для участников»; внешним участникам
   встречи — их гостевые ссылки (ADR-0038). Встрече ставится `room_id` без нового `SEQUENCE` и без писем:
   участники видят комнату в приложении, внешние — на странице встречи.
5. **Права при создании перечитываются** из БД, а не берутся из момента сохранения: участник пространства,
   не гость и не бот, `CREATE_TEMP_ROOMS` (с учётом режима «тариф не активен» — `perm.PlanInactive`),
   пространство не приостановлено, лимиты 20/5; если создание идёт не из запроса организатора (метёлка,
   перенос встречи другим редактором) — ещё политика личности пространства для организатора
   (`identitypolicy.Delivery`, при отсутствии — отказ).
6. **Связь встречи и комнаты.** Перенос встречи двигает конец комнаты (новый конец + 1 ч) и её собственные
   ссылки, истекавшие вместе с ней (как продление, ADR-0044); ждущий запрос просто ждёт нового времени.
   Отмена встречи до создания — ничего не создаётся; после — комната архивируется, как удаление её
   создателем (ссылки отозваны, история в архиве, можно «Вернуть»). Комната, удалённая или истёкшая раньше,
   закрывает встречу по правилам ADR-0044. Комнату, ставшую постоянной или чужой, встреча больше не трогает.

## Последствия
- Клиент: переключатель в диалоге (организатор с `CREATE_TEMP_ROOMS`, без повтора; взаимоисключается с
  выбором комнаты), карточка показывает «Временная комната появится за час до начала».
- Отклонено: временная комната на каждое вхождение серии (v1 — запрет); приватная комната только для
  участников встречи (пришлось бы синхронизировать участников с правами; приватность — через «Доступ»
  комнаты после создания); письмо участникам о появлении комнаты (лишний шум, ссылка уже в приглашении).

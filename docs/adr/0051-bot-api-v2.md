# ADR-0051: Расширенный Bot API (2026-09-30)

> §5 изменён [ADR-0109](0109-bot-rights-like-people.md): закрытые ботам маршруты с проверкой права открыты;
> `botDeny` — только по причинам ADR-0109 §2.

## Контекст
Владелец, 30.09: «расширить API для ботов, чтобы они могли календарь править, всякие действия делать
админские — типа людей переименовать, посмотреть профили, с задачами работать, чаты читать все, к которым
доступ есть». ADR-0031 закрыл ботам часть маршрутов «на всякий случай» (`botDeny` в
`internal/app/botroutes.go`): календарь только на чтение, без свободно/занято, приглашений, бейджей, записи.

## Решение
1. **Принцип ADR-0031 не меняется: бот = пользователь, права только через роли и переопределения.**
   `computePermissions` / `perm.Compute*` без бот-битов; встроенная роль бота — `member`; закрытые комнаты
   и доски (ADR-0029, ADR-0048 «без администраторов») — только по переопределению. Открываем маршруты, где
   отказ был не из-за человеческого намерения или секретов. Токен бота с админскими битами = админ.
2. **Открыто (`botDeny` → `botAllow`), бит — тот же, что у человека:**
   | Маршрут | Бит / условие |
   |---|---|
   | `POST /api/workspaces/{id}/events` | не гость; комната — видимая голосовая; **бот — организатор, но не участник** |
   | `PATCH`, `DELETE /api/events/{id}` | организатор, иначе `MANAGE_ROOM` room встречи или `MANAGE_EVENTS` ws (видимая комната); внешние адреса — только в свою встречу (иначе ссылки комнаты автора и письма от его имени) |
   | `GET …/freebusy`, `POST …/freebusy/suggest` | не гость; боту — только «занято» (без названий и участников внешних событий, ADR-0045) |
   | `GET /api/workspaces/{id}/members/{userId}` (новый, и для людей) | участник; гость — только видимых ему (ADR-0016) |
   | `GET/POST …/invites`, `DELETE …/invites/{inviteId}`, `GET/POST …/invites/email`, `DELETE …/invites/email/{inviteId}` | `INVITE_MEMBERS` ws (ADR-0043); пригласить админом — только владелец |
   | `POST/PATCH/DELETE …/badges…` · `PUT …/members/{userId}/badge` | `MANAGE_MEMBERS` ws · `MANAGE_NICKNAMES` ws + иерархия |
   | `POST/PATCH/DELETE …/sounds…` | `MANAGE_STICKERS` ws |
   | `POST /api/rooms/{id}/admissions/{userId}` | `INVITE_GUESTS` room (как у людей, ADR-0040/0043) |
   | `POST /api/rooms/{id}/recording/start`, `…/stop` | как у людей (`VIEW_ROOM` + `CONNECT`, `allow_recording`) **и `MANAGE_RECORDINGS` ws** |

   Уже работало и теперь описано в docs/19 и SDK: чтение видимых комнат и поиск, задачи, ник участника
   (`MANAGE_NICKNAMES`), кик/бан/роли (`MANAGE_MEMBERS`/`MANAGE_ROLES`), комнаты и категории (`MANAGE_ROOM`).
3. **Календарь для бота-организатора.** Бот не бывает участником встречи (нет строки в `event_attendees`, нет
   RSVP, нет «сегодня»); свою встречу видит как организатор. Письма и `invite.ics` участникам — как от
   человека: `ORGANIZER` — системный отправитель (`SMTP_FROM`), имя — название пространства; в тексте письма
   «Пространство (от имени бота X)»; `Reply-To` нет (у бота нет почты). Гостевые ссылки комнаты внешним
   участникам встреч бота не создаются (ссылки комнат — только люди, ADR-0031): внешние получают письмо со
   ссылкой на страницу встречи. Адреса внешних участников бот видит, только если может править встречу (как
   человек-организатор или менеджер); иначе — без адресов (человек видит маскированные).
4. **Запись — ещё и `MANAGE_RECORDINGS`.** Человек запускает запись, будучи на виду в звонке; бот может
   делать это без присутствия и массово, поэтому ему нужен явный бит пространства. Это проверка в обработчике,
   не бит в `computePermissions`.
5. **Остаются закрыты:** удаление пространства; управление ботами (создание, токены, аватар); SIP-настройки
   (пароль провайдера), GPTunneL, веб-приложения, суперадминка; **голос в согласовании задач** (решение —
   человеческое намерение, ADR-0049); **RSVP** (бот не участник), CalDAV, `me/external-events`,
   `me/events/today`; поиск аккаунта по почте и прямое добавление аккаунта (`invites/lookup`,
   `POST …/members`) — перебор адресов и добавление без согласия; гостевые ссылки комнат; таблица и правка дней
   рождения (день рождения участника бот видит в профиле так же, как люди — скрытый не отдаётся); доступ к
   доске (`PUT /api/boards/{id}/permissions`); удаление, перепроверка и перезагрузка записей; фоны, заметки,
   звонки DM, пароль/почта/сессии.
6. **События.** Gateway: `EVENT_*` боту-организатору приходят как организатору (адреса — по праву править),
   остальным ботам — по `VIEW_ROOM` комнаты встречи; `TASK_*` — по `VIEW_BOARD`; `WORKSPACE_MEMBER_UPDATE` —
   всем участникам. Webhook (ADR-0031 §4) доставляет те же события с той же видимостью (раньше — только
   сообщения и реакции).

## Последствия
- `botroutes.go` + `TestBotRouteTable`; интеграционные тесты на каждый открытый маршрут (с битом — 2xx, без —
  403, закрытые комнаты и доски невидимы). Лимиты `rl:bot:req:` действуют на все маршруты (`auth.Require`).
- Proto: `GET /api/workspaces/{id}/members/{userId}` → `GetMemberResponse {member, open_tasks}` — открытые
  задачи участника (исполнитель) только с досок, которые видит вызывающий, ≤ 50.
- Журнал: сервер пишет строку `bot action` (маршрут, статус, бот, **владелец бота**) на каждое изменяющее
  действие бота из административных маршрутов; журнал доски, как и раньше, пишет актором бота.
- Клиент: в редакторе ролей предупреждение при выдаче административных битов роли, у которой есть боты.
- SDK `packages/bot-sdk`: `bot.calendar.*`, `bot.members.get/setNickname`, `bot.invites.*`, `bot.badges.*`,
  `bot.recording.*`.
- Безопасность: утечка токена бота с админской ролью = утечка админа — выдавать такие роли осознанно
  (предупреждение в UI), токен перевыпускать при подозрении. Второе ревью обязательно (права, auth).

# ADR-0102: OAuth-клиенты пространства без свежего пароля (2026-10-15)

**Статус: принято.** Уточняет [ADR-0054](0054-workspace-identity.md) (п. 8 и контракт
[release-2.0-identity](../plans/release-2.0-identity.md) §8). Номер 0101 занят восстановлением пароля почты.

## Контекст
Владелец, 15.10: вкладка «OAuth-клиенты» просит «Подтвердить пароль» (окно 5 минут), хотя
сессия уже есть; создание приложения падает с «Проверьте введённые данные» или «Уже изменено
кем-то другим». Причины: `ManageOAuth` требовал local reauth не старше 5 минут на всех маршрутах
(включая список); любой отказ валидации и проверка Origin (`Origin == IDENTITY_PUBLIC_ORIGIN`)
превращались в 422 без поля — десктоп, сохранивший сервер-алиас (`app.calab.ru`), получал его
на каждую запись; лимиты (20 клиентов, 2 секрета) и отсутствие Business приходили как 409 и
показывались как конкурентная правка. `http://localhost` в redirect не принимался вообще.

## Решение
1. **Без свежего пароля.** `ManageOAuth` (список, создание, правка, удаление, смена секрета)
   не требует `local_authenticated_at` в окне 5 минут. Остаются: роль owner/admin, запрет
   гостям, entitlement Business/Enterprise, SSO proof при enforced, аудит. Authority:
   `local_account` — без recency; `workspace_sso` — только через свежий SSO proof этого
   workspace (как раньше для enforced); `recovery` — никогда. Почему безопасно: bearer-сессия
   уже аутентифицирует администратора; доступ к данным пользователя RP получает только после
   явного согласия каждого пользователя; секрет показывается один раз; каждая мутация и
   ротация пишутся в аудит. SSO, каталог, bootstrap link, enforcement и глобальные действия
   по-прежнему требуют свежий пароль.
2. **Loopback для всех типов.** `http://localhost[:port]`, `http://127.0.0.1[:port]`,
   `http://[::1][:port]` допустимы как redirect у web, native и SPA (трафик не покидает машину;
   так делают Google и GitHub). Совпадение точное; переменный порт — только native и только
   для IP-литералов (RFC 8252 §7.3). Схема приложения — только native.
3. **Origin маршрутов управления.** Для bearer-маршрутов клиентов строгая проверка
   `Origin == IDENTITY_PUBLIC_ORIGIN` не защищает от CSRF (cookie нет). Принимаются
   `IDENTITY_PUBLIC_ORIGIN` и origin-ы приложения из `PUBLIC_APP_URL*` (как CSRF-проверка
   остального API), при `Sec-Fetch-Site != cross-site`. Отказ — 403 `FORBIDDEN` и info-лог
   с увиденным Origin и маршрутом. Consent `bind`/`decision` (cookie) и публичные OIDC
   endpoints не меняются.
4. **Понятные ошибки.** Валидация клиента — 422 с полем (`name`, `type`, `redirectUris`,
   `allowedOrigins`, `scopes`) и стабильным сообщением; форма проверяет те же правила заранее
   (`features/identity/oauthClientForm.ts`) и показывает текст под полем. 409 PLAN_LIMIT
   лимитов и тарифа называют причину, а не «изменено кем-то другим». Wire-контракт не менялся.

## Последствия
- Украденный bearer администратора позволяет создать клиент без пароля; данные пользователей
  он всё равно получит только через их согласие, а запись видна в аудите. Тот же bearer уже
  даёт чтение чатов пространства — порог защиты не снижается заметно.
- Loopback-redirect у confidential web: код, пойманный локальным процессом, без секрета и
  PKCE verifier не обменять; у SPA — без verifier.
- Origin SPA остаётся только `https://` — SPA на `http://localhost` в разработке не получит
  CORS на token endpoint (кандидат в бэклог, если понадобится).

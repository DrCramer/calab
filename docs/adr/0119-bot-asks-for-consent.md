# ADR-0119: Бот сам просит согласие «от имени» и узнаёт об ответе (2026-10-22)

**Статус: принято.** Дополняет [ADR-0111](0111-bot-acts-for-consenting-member.md) §5 (приглашение) и
отменяет его пункт «Не делаем: события об изменении согласий». Задача CBF-41, решение владельца 22.10.

## Контекст
Пункт «⋯ → Делегировать права» никто не находит: на 20.10 согласий 0 из 14. Опса заводит карточки
DOC/INV/HR только «от имени» заявителя; без согласия карточку не создаёт. Спросить сама она не могла:
`POST …/delegation-invites` для бота был `botDeny`. После «Принять» ей нужен сигнал, чтобы сразу
создать ждущую карточку; людям из Telegram — ссылка на приглашение в Calab.

## Решение
1. **Бот приглашает сам.** `POST /api/workspaces/{id}/bots/{botId}/delegation-invites` — `botAllow`,
   закрыт «от имени» (`ON_BEHALF_ROUTE`). Бот — только для своего `{botId}` (иной — `403
   BOT_NOT_ALLOWED`) и с ролью не `guest` там (`ON_BEHALF_NOT_ELIGIBLE`). Всё остальное как §5:
   цели — люди с ролью не `guest`, не сам бот и не боты (`422`), одно ожидающее на (пространство ×
   бот × участник), лимит `rl:bot-delegation-invite:` 20 сразу и 30 в час на приглашающего (здесь —
   на бота), блокировка бота человеком — отказ. `invited_by` = бот.
2. **Текст — сервера, от бота.** Шаблон «Бот X просит разрешить ему действовать от вашего имени…
   Разрешение даёте только вы» — имя приглашающего-человека в нём не появляется. Необязательный
   `reason` (≤ 200 символов) показывается строкой «Зачем, со слов бота: …» и очищается до простого
   текста: одна строка, буквы, цифры, пробелы и обычная пунктуация; без `@` (упоминание выглядело бы
   именем человека), `/` (ссылки), разметки и управляющих символов. Тот же фильтр — имени бота в
   шаблоне (бот сам меняет своё имя, `PATCH /api/me`). Остальное — как раньше: кнопки
   `delegation_accept` / `delegation_decline` для одного приглашённого; засчитывается только его клик
   из его сессии (маршрут кликов `botDeny`, «от имени» закрыт); правка сообщения ботом гасит кнопки.
   Отменить приглашение, дать или отозвать согласие бот по-прежнему не может (`botDeny`).
3. **Повтор после отказа.** «Отказаться» (кнопка или `DELETE …/delegation-invites/{свой id}`)
   записывается в `bot_delegation_declines` (миграция `00110`). 7 дней такого участника не приглашает
   никто: он пропускается, а если пропущены все из запроса — `409 DELEGATION_INVITE_DECLINED` с
   `Retry-After`, `used` = секунды до конца, `limit` = 7 дней. Своё согласие (`PUT`) удаляет запись.
4. **Ответ со ссылкой.** `GetBotResponse.sent`: для каждого отправленного приглашения (а боту — и для
   уже ожидающих из запроса) `BotDelegationInviteMessage {user_id, message_id, room_id, url, created}`.
   `url` = `PUBLIC_APP_URL/m/<room>/<message>` — обычная ссылка на сообщение (веб-клиент и
   приложение её открывают; universal links — CBF-40). Токенов в ней нет: открыть DM может только
   его участник.
5. **Событие `BOT_DELEGATION`** (`DispatchEvent.bot_delegation`, `BotDelegationChange {id,
   bot_user_id, workspace_id, user_id, state, at}`), `state` — `granted` (новое согласие: `PUT` или
   «Принять»), `revoked` (`DELETE …/delegations/{свой id}`), `declined` (отказ, см. п. 3). Только
   этому боту: его user-канал gateway (сессии людей не получают, как `contact_shared`) и вебхук.
   Доставка вебхука ставится в той же транзакции, что и изменение (как `BOT_CALLBACK`); декоратор
   публикатора её не дублирует. Согласие, переставшее действовать по другой причине (выход, гость),
   события не шлёт — бот читает `GET …/bots/{botId}`.
6. SDK: `bot.inviteDelegation(workspaceId, userIds, reason?)`, событие `botDelegation`.

## Последствия
- Бот может слать людям приглашения сам — не чаще лимита и не чаще раза в 7 дней после отказа.
  Права он по-прежнему получает только кликом самого человека.
- Второе ревью безопасности — обязательно (путь согласия «от имени»).

## Альтернативы
- **Deep link на диалог «Делегировать права»** вместо ссылки на сообщение: потребовал бы нового
  маршрута клиента; ссылка на DM уже работает и ведёт ровно на кнопку.
- **Кулдаун в Redis.** Проще, но теряется при сбросе; отказ — решение человека, хранится в Postgres.

# ADR-0031: Боты и Bot API (2026-09-27, релиз 0.7.0)

> Таблица маршрутов (§2) изменена [ADR-0109](0109-bot-rights-like-people.md): закрыто только то, что роль решить
> не может; секции таблицы — с причиной.

## Контекст
Владелец: «нужны боты и API к ним, что-то простое, как в Telegram: боту можно выдать те же права, что
юзеру; он может по API зайти в комнату, видеть кто там, слышать всех и отдавать звук в канал; писать в
чат и видеть, что пишут». Нужна нормальная архитектура, отдельный релиз 0.7.0, публичная документация.

## Решение
1. **Бот — это пользователь** (`users.is_bot`), созданный из «Настройки пространства → Боты» (владелец /
   `MANAGE_WORKSPACE`; лимит на пространство — план, ADR-0024). Имя, аватар, описание, «владелец бота»
   (`bots.owner_user_id`). Бот автоматически становится участником этого пространства с ролью **member**;
   права — **только через роли и переопределения комнат**, как у людей (`computePermissions` не меняется;
   бот не может быть owner/admin по встроенной роли, но роль с любыми битами ему выдать можно). В других
   пространствах бот появляется, когда его туда приглашает админ («Добавить бота» по ссылке
   `/bots/<username>`), как в Telegram. Гостевые ссылки ботам не выдаются.
2. **Аутентификация — токен бота** `calab_bot_<botId>_<секрет 32 байта base64url>`: показывается один раз при
   создании и при «Перевыпустить», хранится хэшем (`sha256`, токены высокоэнтропийные), отзыв — «Отозвать».
   Тот же заголовок `Authorization: Bearer …`: `auth.Require` распознаёт префикс `calab_bot_` и даёт
   `Identity{UserID, IsBot: true}` без сессий и refresh. Лимиты: `rl:bot:` — 30 запросов/с и 20 сообщений/мин
   на бота (env `BOT_RATE_*`). Боту закрыты пользовательские эндпоинты: пароль/почта/сессии/устройства,
   создание пространств, инвайты, оплата, суперадминка, настройки профиля кроме имени/аватара/описания.
3. **REST — тот же API**, что у клиента (docs/05), без отдельного «Bot API»: сообщения, реакции, файлы,
   стикеры (отправка сообщением-стикером; **создание паков и добавление стикеров в пак по API** — при
   праве `MANAGE_STICKERS` у бота, ADR-0030), закреп, участники, комнаты, DM (бот может писать в DM участникам общих пространств; человек
   может в любой момент «Заблокировать бота»). Ответы и события — protojson, как сейчас. Дополнительно для
   ботов: `GET /api/me` отдаёт `is_bot`, `PUT /api/bots/me/commands` (список команд `{name, description}`),
   `PATCH /api/bots/me` (описание, «about»).
4. **Realtime — тот же WS-gateway** (`/gateway`, IDENTIFY токеном бота → READY + события по правам
   `VIEW_ROOM`: `MESSAGE_CREATE/UPDATE/DELETE`, `REACTION_*`, `VOICE_STATE`, `PRESENCE_UPDATE`, `TYPING`,
   `ROOM_*`, `WORKSPACE_MEMBER_*`). Второй транспорт — **webhook**: `PUT /api/bots/me/webhook {url, secret}`
   (только https), сервер шлёт `POST` с JSON события и подписью `X-Calab-Signature: sha256=HMAC(secret, body)`,
   ретраи с backoff 1 мин → 1 ч в течение суток через outbox-очередь (`bot_webhook_deliveries`), отключение
   после суток ошибок с уведомлением владельцу бота. Long-poll `GET /api/bots/me/updates?offset=` — бэклог.
5. **Голос — через LiveKit, не через наш API.** Бот делает `POST /api/rooms/{id}/join` (те же права
   `CONNECT/SPEAK/STREAM`, тот же LiveKit-grant, docs/04) и получает `url + token`; звук слушает и публикует
   LiveKit-клиентом (`@livekit/rtc-node`, `livekit` Python, `livekit/server-sdk-go` + `lksdk`): подписка на
   треки всех участников, публикация своего аудио-трека (Opus 48 кГц), опционально экран/камера при `STREAM`/
   `VIDEO`. Наш сервер видит бота как участника: строка в списке, значок «БОТ», индикация речи, серверный
   mute/kick действуют как на человека. Проксировать медиа через REST не будем — LiveKit это и есть медиа-API
   (задержка, масштаб).
6. **Команды и упоминания.** Бот регистрирует команды; композер показывает подсказки при вводе `/` (по ботам
   комнаты); сообщение, начинающееся с `/cmd` или `/cmd@bot`, доставляется всем как обычное, а событие для
   бота содержит `command {name, args, bot_user_id}`. Упоминание `@бот` — обычное упоминание (`@<id>` в тексте события
   `MESSAGE_CREATE`, как у людей). Кнопки под сообщением (inline keyboard) — фаза 3 (бэклог).
7. **UI.** Значок «БОТ» у имени (список, пузырь, профиль); профиль бота — описание, «Команды», «Владелец»,
   «Добавить в пространство…»; «Настройки пространства → Боты»: список, «Создать бота» (имя → токен один раз),
   «Перевыпустить токен», «Отозвать», «Удалить», webhook-статус (последняя доставка, ошибки), лимиты.
   Боты не показываются в «в сети/не в сети» как люди — секция «Боты» в списке участников (как Discord).
8. **SDK и документация.** `packages/bot-sdk` (TypeScript, ESM, без Node-зависимостей кроме `ws`): `new Bot(token,
   {server})`, `bot.on('message', …)`, `bot.send(roomId, text|{sticker,files})`, `bot.commands([...])`,
   `bot.voice.join(roomId)` → `{url, token}` + helper для `@livekit/rtc-node`. Примеры `examples/bots/echo`,
   `examples/bots/voice-echo` (слушает и повторяет), `examples/bots/tts` (озвучивает текст через внешний TTS).
   **Документация для разработчиков** — `docs/19-bot-api.md` (публичный, на русском и английском:
   быстрый старт за 5 минут, токен, REST-эндпоинты с примерами `curl`, события gateway, webhook и подпись,
   голос через LiveKit с примером на Node и Python, команды, лимиты, ошибки) + страница `/bots` на лендинге
   и ссылка из «Настройки → Боты». Генерируется из одного источника (Markdown в репо), не расходится с proto.

## Последствия
- Миграция 00029: `users.is_bot`, `bots(user_id PK, owner_user_id, workspace_id, token_hash, token_prefix,
  description, webhook_url, webhook_secret_enc, webhook_disabled_at, created_at, revoked_at)`,
  `bot_commands`, `bot_webhook_deliveries`; proto: `User.is_bot`, `Bot`, `BotCommand`, события `BOT_*`.
- Сервер: распознавание токена в `auth`, allow-list эндпоинтов для ботов (тег на маршруте), лимиты, webhook-
  outbox, парсер команд в `messages`, роль member при создании, секция «Боты» в READY. LiveKit-grant без
  изменений.
- Безопасность: токен не в URL и не в логах; второе ревью (auth-путь) обязательно; бот не видит ничего сверх
  `VIEW_ROOM`; ограниченные комнаты (ADR-0029) действуют; webhook только https и не на приватные адреса
  (SSRF-фильтр как у превью ссылок).
- Фазы 0.7.0: (1) сервер + токены + gateway + команды + UI настроек/значок; (2) SDK, примеры, docs/19 и
  лендинг; (3) webhook и inline-кнопки — если не успеваем, в 0.7.1.

## Уточнения после реализации (28.09)
Пути и методы в тексте выше приведены к серверу: gateway `/gateway`, команды `PUT`, вход в голос `POST /api/rooms/{id}/join`, упоминания — `@<id>` в тексте. Публичная документация — `docs/19-bot-api.md` (ru) и `docs/19-bot-api.en.md` (en), SDK — `packages/bot-sdk`, примеры — `examples/bots`. Helper для `@livekit/rtc-node` в SDK не включён (одна зависимость `ws`), голосовой код — в примерах.

Бот с `VIEW_ROOM` читает полный сохранённый транскрипт записи, доступной в комнате (включая живую пересланную карточку, ADR-0033), через `GET /api/rooms/{id}/recordings/{rid}/transcript`; ограниченные комнаты и удаление записи проверяются как у человека. Управление записью остаётся закрыто. Точечное чтение `GET /api/rooms/{id}/messages/{messageId}` возвращает существующий `Message` без обёртки и соблюдает границу очищенной истории DM. Оба маршрута используют обычную проверку доступа к комнате.

Кнопки под обычными сообщениями реализованы отдельным аддитивным контрактом: [ADR-0047](0047-bot-inline-buttons.md).

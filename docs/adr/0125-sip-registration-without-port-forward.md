# ADR-0125: Регистрация у SIP-провайдера без проброса порта — агент как клиент за NAT (2026-10-22)

**Статус: принято (22.10, владелец), реализовано (CBF-76).** Меняет §4–§5 [ADR-0121](0121-sip-inbound-registration.md)
(публичный порт 5080 и Contact `<токен>@<публичный IP>:5080`); всё остальное ADR-0121 — модель аккаунта,
digest, B2BUA к LiveKit SIP, фильтр источников, канал к API — без изменений. Медиа (RTP) не меняется:
его по-прежнему ведёт LiveKit SIP.

## Контекст

По ADR-0121 агент `calab-sipreg` кладёт в Contact/Via `SIP_REGISTRAR_PUBLIC_IP:5080` и ждёт INVITE
провайдера на этом порту. Это требует публичного адреса и открытого (в k8s — проброшенного) порта 5080
udp/tcp. Владелец (22.10): целевая схема — «мы SIP-клиент, зарегистрированный у провайдера (Plusofon), как
софтфон за домашним роутером»: никакого проброса 5080, никакого публичного IP в конфиге; по умолчанию всё
работает только с настройками аккаунта из интерфейса.

## Решение

**Режим «поток» (flow) — по умолчанию.** Если `SIP_REGISTRAR_PUBLIC_IP` (и `SIP_REGISTRAR_STUN`) не заданы,
агент держит к каждому регистратору постоянный поток (RFC 5626 «flow») и получает INVITE по нему же:

- **TCP (транспорт аккаунта `tcp`)**: агент сам открывает одно долгоживущее соединение на адрес
  регистратора (все аккаунты на этом адресе делят его) и отдаёт его в sipgo через «слушатель», который
  возвращает это соединение из `Accept` (у sipgo нет API принять чужое соединение; с этого момента sipgo
  читает его и шлёт ответы и запросы на этот адрес по нему же, как по любому принятому). Своё TCP sipgo
  в этом режиме не открывает (dialer отказывает): запрос к провайдеру без потока падает, а не уходит
  мимо. Живость: TCP keepalive ОС (15 с / 5 с × 3), ping двойным CRLF каждые 20 с (RFC 5626 §4.4.1) —
  если регистратор отвечает pong, его отсутствие 10 с закрывает поток; OPTIONS — по `reg_keepalive_sec`
  аккаунта, два без ответа закрывают поток. Разрыв → сразу новое соединение и REGISTER; если поток рвётся
  раньше чем через минуту после регистрации — экспоненциальный backoff 5 → … → 300 с (`failed/tcp: …`).
- **UDP (по умолчанию у Plusofon)**: поток — NAT-привязка UDP-сокета агента (`SIP_REGISTRAR_PORT`, локальный,
  по умолчанию 5080) к адресу регистратора; запросы уходят с этого сокета, INVITE приходят обратно через
  ту же привязку. Keepalive `OPTIONS` — не реже раза в 20 с, даже если в аккаунте keepalive выключен или
  больше (привязка — единственный путь к нам; UDP-таймауты conntrack/облачных NAT — 30–120 с); с
  `Flow-Timer` регистратора — не реже 80 % его.
- **Contact из того, что видит регистратор.** Первый REGISTER несёт локальный адрес (свой конец TCP или
  локальный IP маршрута к регистратору); ответ с `Via received/rport` (RFC 3581, `;rport` в Via) — агент
  перерегистрируется с увиденным адресом, в том же REGISTER снимая прежний Contact (`expires=0`), и тот же
  адрес кладёт в Via и в Contact диалогов. Ответ на OPTIONS с другим адресом (NAT переназначил порт) —
  перерегистрация сразу. Новое TCP-соединение — новое сопоставление: адрес узнаётся заново.
- **RFC 5626 outbound**: в Contact REGISTER `;ob`, `reg-id=1`, `+sip.instance="<urn:uuid:…>"` (UUIDv5 от
  `contact_user` — стабилен между перезапусками: регистратор с поддержкой outbound заменяет привязку упавшего
  пода), `Supported: path, outbound`. Регистратор без поддержки игнорирует параметры; аварийный выключатель —
  `SIP_REGISTRAR_OUTBOUND=off`.
- **Срок регистрации** в этом режиме — не больше 300 с (обновление на половине): привязка, оставшаяся от
  упавшего пода или мёртвого потока, живёт у провайдера не дольше 5 мин. Перезапуск пода → снимок от API →
  REGISTER сразу; штатная остановка снимает регистрации (`Expires: 0`).
- **Входящие по потоку**: INVITE приходит с адреса регистратора — фильтр источников (адреса аккаунта ∪
  резолв регистратора) прежний, `contact_user` в Request-URI определяет аккаунт, ответы и запросы в диалоге
  (BYE, re-INVITE, INFO) к провайдеру уходят по тому же потоку (на адрес, с которого пришёл INVITE, RFC 5626
  §5.3), а не на Contact провайдера. Leg B к LiveKit SIP — как раньше; адрес агента для LiveKit SIP —
  loopback, если LiveKit SIP на loopback, иначе локальный IP маршрута к `LIVEKIT_SIP_ADDR` (агент и LiveKit
  SIP должны видеть друг друга напрямую: тот же хост, под или сеть).

**Режим «проброс» (forward) — прежний, необязательный.** `SIP_REGISTRAR_PUBLIC_IP` (или `SIP_REGISTRAR_STUN`)
включает поведение ADR-0121: Contact `<токен>@<IP>:SIP_REGISTRAR_PORT`, TCP-слушатель на этом порту, порт
должен быть доступен провайдеру. TCP-регистрация и здесь идёт по собственному потоку агента. STUN по
умолчанию больше не используется.

## Почему так

1. **Это то, как работают софтфоны** (Zoiper, Linphone, pjsip): `rport` + переписывание Contact + keepalive +
   один поток. Провайдер, выдающий SIP-логины для софтфонов и IP-телефонов (как Plusofon), рассчитан на
   абонентов за NAT; проброс порта и публичный IP для этого не нужны.
2. **Своё соединение, а не соединение sipgo**: только так агент знает, когда поток умер (чтение вернуло
   ошибку), может его закрыть и пинговать, и не допускает второго соединения «в обход» (sipgo открыл бы
   новое на любой запрос без соединения, и INVITE пришёл бы туда, где его не ждут).
3. **Один поток на адрес регистратора**: пул sipgo держит одно соединение на удалённый адрес; два потока
   к одному адресу затирали бы друг друга. Аккаунты одного провайдера на одном адресе делят поток, аккаунт
   определяется по `contact_user`, как и раньше.
4. Отклонено: **STUN вместо `rport`** — STUN узнаёт адрес относительно STUN-сервера, а не регистратора
   (симметричный NAT даёт другой порт), и не держит привязку к регистратору; **короткий expires вместо
   keepalive** — каждая перерегистрация — digest-обмен (2 запроса), провайдеры ограничивают частоту REGISTER;
   **TLS/WSS** — позже (ADR-0121 §4), схема та же.

## Риски и что проверить в проде (Plusofon)

- **Несколько egress-IP кластера.** Провайдер пускает только адреса из белого списка. Если у узлов/NAT-шлюзов
  кластера несколько исходящих адресов, поток (и каждое переподключение) может выйти с любого из них —
  **в белый список Plusofon вносятся все egress-IP**, иначе регистрация то проходит, то нет. Надёжнее —
  один фиксированный egress (NAT-шлюз со статическим адресом) для пода агента.
- **INVITE должны приходить с адреса регистратора.** NAT пропускает внутрь только ответы на наш поток: INVITE
  с другого адреса провайдера (отдельный прокси) по UDP до агента не дойдёт, по TCP придёт только по
  нашему соединению. Если в логах регистрация есть, а звонков нет — спросить провайдера, с какого адреса он
  шлёт INVITE, и попросить слать по зарегистрированному потоку (обычное поведение для абонентов за NAT).
- Не проверено без провайдера: ставит ли Plusofon `received/rport` и уважает ли `;ob`/`reg-id`; какой
  `expires` выдаёт при запросе 300 (если `423` — агент берёт `Min-Expires`); отвечает ли на CRLF-ping по TCP.
- Один под агента (как и раньше): два пода с одним `contact_user` дали бы две привязки.

## Последствия

- Деплой: агент, его токен `SIPREG_AGENT_TOKEN` (в env агента и API), egress-IP в белый список провайдера.
  Порт 5080 наружу не открывается и не пробрасывается; `SIP_REGISTRAR_PUBLIC_IP` не задаётся.
- Код: `apps/server/cmd/sipreg/flow.go` (потоки), `registration.go` (Contact из `received/rport`, снятие
  старого Contact, keepalive, срок), `b2bua.go` (диалог по потоку), `main.go` (режимы, env).
- Тесты: `cmd/sipreg/flow_test.go` — INVITE по TCP-соединению регистрации (у агента нет TCP-порта),
  переподключение и снятие старого Contact, потеря pong, Contact из `received/rport` и его смена по OPTIONS,
  UDP-keepalive при выключенном keepalive аккаунта, режим проброса.

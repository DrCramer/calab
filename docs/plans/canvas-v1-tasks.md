## Проверка H8

Без Playwright (браузеров на машине нет): два–три настоящих клиента — `lib/ySync.ts`/`lib/canvasSync.ts` и модель `lib/canvas/doc.ts` с глобальным `WebSocket` Node ≥ 22 — работают с живым Go-сервером. Нужны Postgres 17+ и Valkey/Redis (LiveKit не нужен). Пример для локальных контейнеров разработки (`pnpm infra:dev`: Postgres `localhost:55432`, Valkey `localhost:56379`; подставь свои порты):
- База: `createdb calaba_h8` (или `docker exec <postgres> psql -U calaba -c 'create database calaba_h8'`).
- Сервер (в `apps/server`; миграции применяются сами): `DATABASE_URL=postgres://calaba:calaba@localhost:55432/calaba_h8 REDIS_URL=redis://localhost:56379/8 REDIS_KEY_PREFIX=h8: JWT_SECRET=<32+ символов> REGISTRATION_MODE=open EMAIL_VERIFICATION=optional HTTP_ADDR=127.0.0.1:3078 PUBLIC_APP_URL=http://localhost:4178 STORAGE_PATH=/tmp/h8 AUTH_RATE_BURST=1000 AUTH_RATE_PER_MINUTE=1000 go run ./cmd/server`.
- REST: `tools/canvas-walk.sh http://127.0.0.1:3078 [dir]` — 65 шагов теми же запросами, что `services/canvas.ts` (два пользователя, приглашение, папка и холсты, переименование, перенос, права GET/PUT, приватный холст, поиск по названию, журнал, настройки, корзина/восстановление/удаление, `take-over`, отказы 403/404/409); с `dir` сохраняет ответы в `apps/desktop/src/renderer/services/__fixtures__/canvas` (читает `services/canvas.wire.test.ts`).
- Сходимость: `CALABA_CANVAS_LIVE=1 CALABA_LIVE_BASE=http://127.0.0.1:3078 pnpm -F @calaba/desktop exec vitest run canvasSync.live` (≈ 40 с; тест сам регистрирует людей, пространство и холсты; без переменной файл пропущен, обычный `pnpm test` его не запускает). С `CALABA_CANVAS_DUMP=<dir>` дописывает фикстуры, которым нужен документ: `versions`, `list-compacted`, `search-text`.
- Что проверяет (11 сценариев): стикер/фигура/коннектор A → B и равные снимки состояния (вектор и набор удалений); одновременные правки полей, удаление против переноса, `Y.Text` с двух концов; awareness (курсор, поздний участник, уход); только просмотр (`readonly`, сервер закрывает 4003 на UPDATE и SNAPSHOT_POST, неверный клиент получает `onFatal(4003)`); приватный холст, не участник, бот — 4003, папка/корзина/чужой id — 4404, плохой токен — 4004; реконнект с правками оффлайн в обе стороны; компакция по бездействию (размер, превью, первая версия, поиск по тексту объекта); `COMPACT_REQUEST` после 1 МиБ; правка > 64 КиБ одной транзакцией (снимок с `broadcast`) и пачкой (несколько кадров), состояние > 4 МиБ (`onTooLarge`, сервер молча не принимает); восстановление версии на живом документе; задержки.
- Цифры (локальный сервер, Node): правка A→B и B→A «как набрана» — медиана ≈ 210 мс (из них 200 мс — пакетирование клиента), по сети и серверу после `flush()` — медиана 4–8 мс (макс. 13 мс); awareness ≈ 3 мс; реконнект после обрыва — 0,5 с (джиттер 0); загрузка холста в 1,1 МиБ поздним участником — ≈ 40 мс; компакция по бездействию — 3,05–3,1 с после последней правки; восстановление версии у второго клиента — ≈ 210 мс. В браузере через интернет — ближе к цифрам Вики (0,1–0,8 с).
- Расхождения клиент↔сервер: форма ответов совпала с клиентскими схемами; сервер пишет значения по умолчанию (`name:""`, `parentId:""`, `docSize:0`, `trashedBy:""`, `nextCursor:""`) — клиент читает оба вида; `Struct` журнала — `snake_case` (`parent_id`, `parent_name`, `target_type`); микросекундные метки читаются с точностью до мс; мок исправлен по серверу: перенос папки в своё поддерево — 409 (не 422), удаление не из корзины — 409, у результата поиска есть `path` (имена предков) и маркеры `\u0002…\u0003` в сниппете.
- Что делает сервер, о чём стоит знать: `COMPACT_REQUEST` приходит тому, кто пишет (а не всей комнате), и только на следующем UPDATE после порога (проверка не чаще раза в 2 с); при обрыве сокета сервер не рассылает удаление курсора (у остальных он исчезает через 30 с, `destroy()` шлёт удаление сам); `SNAPSHOT_POST` > 4 МиБ сервер молча игнорирует (сокет остаётся); состояние > 4 МиБ клиент не шлёт (`onTooLarge`).
- Остановить: завершить сервер (`pkill -f cmd/server` или Ctrl-C), `dropdb calaba_h8` (`docker exec <postgres> psql -U calaba -c 'drop database calaba_h8'`), при желании очистить ключи `h8:*` в Redis DB 8 и `/tmp/h8`.
